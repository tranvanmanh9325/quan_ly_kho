# Warehouse Management Backend Project Rules

This document defines the engineering standards, architecture patterns, AI collaboration guidelines, and operational workflows for the Warehouse Management Backend project.

---

## 1. Project Overview and Tech Stack

- **Project:** Warehouse Management System (Backend RESTful API)
- **Language:** Python 3.14+
- **Framework:** Django 6.1+ with Django REST Framework (DRF) 3.18+
- **Database:** PostgreSQL 18.x running locally via `psycopg2-binary`
- **Environment:** Local virtualenv (`venv`), configured via `.env` file
- **Authentication:** Token Authentication (`rest_framework.authtoken`) and Basic Authentication

---

## 2. Core Principles for AI and Team Collaboration

- **Human in the Loop:** AI serves as an accelerator. Developers must thoroughly understand, review, and explain every single line of code generated by AI before committing or opening a pull request.
- **Plan Before Code:** For any new feature or structural change, outline the step-by-step plan (models, serializers, endpoints, tests) before writing implementation code.
- **DRY and Clean Architecture:** Strictly follow the Don't Repeat Yourself principle. Keep ViewSets thin; encapsulate domain logic inside Model methods or dedicated service modules.
- **Zero Security Leaks:** Never hardcode credentials, secrets, or database URLs in source code. All sensitive data must be read from environment variables via `python-dotenv`.

---

## 3. Coding Conventions and Standards

### Python and Django Standards

- Follow PEP 8 guidelines strictly (4 spaces indentation, 79-88 character line limit where practical).
- **Naming Conventions:**
  - Variables, functions, and model attributes: `snake_case` (e.g. `current_total_quantity`, `adjust_stock`)
  - Classes, Models, and Serializers: `PascalCase` (e.g. `WarehouseViewSet`, `ProductSerializer`)
  - Status constants and choices: `UPPER_SNAKE_CASE` (e.g. `IN_STOCK`, `LOW_STOCK`, `OUT_OF_STOCK`)
  - Database table names: Follow Django conventions (`warehouse_warehouse`, `warehouse_product`)
- **Code Comments:** Write all comments and docstrings in English. Explain *why* a particular decision or edge case handling was implemented, rather than stating *what* the code does.

### RESTful API Conventions

- **Endpoint Naming:**
  - Always use lowercase plural nouns for resource collections: `/api/v1/warehouses/`, `/api/v1/products/`.
  - Nested sub-resources: `/api/v1/warehouses/{id}/products/`.
  - Custom RPC-style actions: Use hyphenated kebab-case: `/api/v1/products/{id}/adjust-stock/`.
- **Authentication Header:**
  - Client requests must include the header: `Authorization: Token <token_key>`.
- **Standard HTTP Status Codes:**
  - `200 OK`: Successful resource retrieval, update, or action execution.
  - `201 Created`: Successful resource creation via `POST`.
  - `204 No Content`: Successful resource deletion via `DELETE`.
  - `400 Bad Request`: Validation failure, invalid request body, or business rule violation (e.g. negative quantity, capacity overflow).
  - `401 Unauthorized`: Request missing authentication credentials or invalid token.
  - `403 Forbidden`: Authenticated user lacks permission for the specific action.
  - `404 Not Found`: Resource ID does not exist in the database.
- **Error Response Structure:**
  - Return JSON objects with explicit descriptive fields: `{"error": "Chi tiết lỗi"}` or `{"field_name": ["Lỗi cụ thể"]}`.

### Git Commit Conventions

- Commit messages must strictly follow the Conventional Commits specification in English:
  - `feat: add warehouse stock adjustment endpoint`
  - `fix: resolve capacity overflow validation check`
  - `refactor: extract stock status calculation to model method`
  - `test: add unit tests for warehouse crud and auth`
  - `docs: update api documentation and postman collection`

## 4. Database and ORM Guidelines

- **Query Optimization:**
  - Always use `select_related('warehouse')` when querying products to prevent N+1 query problems.
  - Use Django aggregate and annotate methods (`Sum`, `Count`) for computing summary metrics rather than looping in Python memory.
- **Data Integrity and Validation:**
  - Implement validation logic in model `clean()` methods to ensure constraints are enforced both in API calls and through the Django Admin interface.
  - Call `self.full_clean()` inside `save()` when model-level invariants must be preserved.
- **Migrations:**
  - Review migration files before applying them.
  - Never edit applied migration files manually; generate new migration files using `makemigrations`.

---

## 5. Testing Requirements

- Every new model or endpoint must be accompanied by comprehensive tests in `warehouse/tests.py`.
- Use `rest_framework.test.APITestCase` for all API-level testing.
- Test suites must verify:
  - Happy path status codes (200, 201, 204)
  - Negative values and validation rejections (400)
  - Non-existent resource lookups (404)
  - Unauthenticated access restrictions on protected endpoints (401)
  - State machine transitions (e.g. automatic status updates based on inventory thresholds)
- Ensure all tests pass with `python manage.py test` before pushing changes.
